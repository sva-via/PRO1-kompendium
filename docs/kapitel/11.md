# Kapitel 11 – Associationer: En-til-mange

## 1. Introduktion

Session 11 bygger videre på arbejdet fra Session 10.

Tidligere var fokus på relationer mellem objekter.

Session 11 fokuserer specifikt på:

- en-til-mange-associationer
- samlinger i objekter
- arrays kontra `ArrayList`
- objektsamarbejde
- responsibility (ansvar) i samlingsklasser
- komposition med samlinger
- aggregering med samlinger
- sikker returnering af samlinger

Målet er at designe objekter, der korrekt administrerer grupper af andre objekter.

---

## 2. En-til-mange-relationer

En en-til-mange-relation betyder:

> Ét objekt administrerer flere relaterede objekter.

Eksempler:

- en `Notebook` indeholder mange noter
- en `Playlist` indeholder mange sange
- en `GradeList` indeholder mange karakterer
- en `SchoolClass` indeholder mange studerende

Eksempel:

![Notebook 1 ---- * PriorityNote](../images/Notebook.png)

En notesbog kan indeholde mange noter.

---

## 3. Samlinger i objekter

Objekter administrerer ofte samlinger internt.

Eksempel:

```java
public class Notebook
{
  private PriorityNote[] notes;
  private int size;
}
```

Notesbogen har responsibility for:

- at tilføje noter
- at fjerne noter
- at finde noter
- at beskytte sine invarianter

Selve samlingen er normalt privat.

---

## 4. Arrays kontra ArrayList

En-til-mange-relationer kan implementeres med:

### Arrays

Eksempel:

```java
private PriorityNote[] notes;
```

Fordele:

- fast capacity (kapacitet)
- eksplicit håndtering af size (størrelse)
- forudsigelig struktur

Ulemper:

- manuel ændring af størrelse
- manuel flytning af elementer
- mere implementeringsarbejde

---

### ArrayList

Eksempel:

```java
private ArrayList<PriorityNote> notes;
```

Fordele:

- dynamisk størrelse
- enklere implementering
- automatisk ændring af størrelse

Ulemper:

- lidt mindre kontrol

Efter Session 9:

- arrays er velegnede, når størrelsen er fast
- `ArrayList` foretrækkes, når størrelsen ændrer sig dynamisk

---

## 5. Eksempel: Notebook

Eksempel på struktur:

```java
public class Notebook
{
  private int size;
  private PriorityNote[] notes;
}
```

Notesbogen har responsibility for at administrere sine noter.

Noterne bør ikke kunne manipuleres direkte udefra.

---

## 6. Tilføjelse af objekter

Eksempel:

```java
public void addNote(String note)
{
  notes[size] = new PriorityNote(note);
  size++;
}
```

Notesbogen opretter og administrerer selv sine noteobjekter.

Dette er et eksempel på responsibility.

---

## 7. Komposition og responsibility

Eksempel:

```java
notes[size] = new PriorityNote(note);
```

Notesbogen opretter selv objektet.

Dette er et tegn på komposition.

Komposition betyder:

- ejerskab
- responsibility for objektets levetid
- en stærk relation

Hvis notesbogen forsvinder, forsvinder noteobjekterne også.

---

## 8. Søgning i samlinger

Samlinger gennemløbes ofte ved hjælp af løkker.

Eksempel:

```java
public int indexOfMostImportantNote()
{
  for (int i = 0; i < size; i++)
  {
    if (isHighPriorityNote(i))
    {
      return i;
    }
  }

  return -1;
}
```

Gennemløb af samlinger bliver stadig vigtigere.

---

## 9. Returnering af information

Eksempel:

```java
public String getMostImportantNote()
{
  int index = indexOfMostImportantNote();

  if (index > -1)
  {
    return notes[index].getNote();
  }

  return null;
}
```

En metode kan samarbejde med andre metoder.

God objektorienteret design bygger ofte større metoder op af mindre responsibilities.

---

## 10. Fjernelse af objekter

Arrays kræver flytning af elementer.

Eksempel:

```java
public void removeNote(int index)
{
  for (int i = index; i < size - 1; i++)
  {
    notes[i] = notes[i + 1];
  }

  notes[size - 1] = null;
  size--;
}
```

Vigtige idéer:

- flyt de resterende elementer
- ryd ubrugte pladser
- opdatér `size`

Objektet beskytter sin egen samling.

---

## 11. ArrayList gør håndtering af samlinger enklere

Eksempel:

```java
private ArrayList<Car> cars;
```

Søgning:

```java
for (int i = 0; i < cars.size(); i++)
{
  if (cars.get(i).getMake().equals(make))
  {
    // ...
  }
}
```

`ArrayList` fjerner meget af kompleksiteten ved manuel håndtering af arrays.

---

## 12. Sikker returnering af arrays

Nogle gange returnerer objekter arrays.

Kendt størrelse:

```java
Car[] cars = new Car[numberOfCars];
```

Ukendt størrelse:

```java
ArrayList<Car> carList =
    new ArrayList<>();
```

Senere:

```java
return carList.toArray(cars);
```

Samlinger gør det nemt at opbygge resultat-arrays dynamisk.

---

## 13. Size kontra capacity

Session 11 vender tilbage til en vigtig forskel.

### Size

Antallet af faktisk gemte elementer.

Eksempel:

```java
size
```

### Capacity

Den maksimale lagerkapacitet.

Eksempel:

```java
notes.length
```

Arrays kræver ofte begge begreber.

`ArrayList` skjuler håndteringen af capacity internt.

---

## 14. Responsibility i samlingsklasser

Den klasse, der ejer samlingen, bør administrere den.

God løsning:

```java
notebook.addNote("Remember PRO1")
```

Mindre god løsning:

```java
notebook.getNotes()[0] = note;
```

Objekter bør beskytte:

- samlingens invarianter
- samlingens konsistens
- gyldig state

Responsibility er fortsat det centrale princip.

---

## 15. Test af samlingsklasser

Samlingsklasser kræver grundig test.

Eksempel:

```java
@Test void testMostImportantNote()
{
  Notebook notes =
      new Notebook(10);

  notes.addNote("Check email");

  notes.addHighPriorityNote(
      "Make PRO1 exercises");

  assertEquals(
      "Make PRO1 exercises",
      notes.getMostImportantNote());
}
```

Vigtige testområder:

- tilføjelse af objekter
- fjernelse af objekter
- søgning
- tomme samlinger
- grænsetilfælde

## 16. Arrays eller ArrayList?

Spørg først:

### Fast antal?

Eksempel:

```text
Album → Songs
```

Et array kan være det rigtige valg.

---

### Dynamisk antal?

Eksempel:

```text
Playlist → Songs
```

`ArrayList` er ofte det bedste valg.

Vælg datastrukturen ud fra domænets responsibility.

---

## 17. Samarbejde mellem objekter

Samlingsklasser samarbejder med de objekter, de indeholder.

Eksempel:

```java
notes[index]
    .isHighPriorityNote()
```

Notesbogen delegerer responsibility for noter til noteobjektet.

Objekter samarbejder i stedet for at gøre alting selv.

---

## 18. Typiske begynderfejl

Almindelige fejl:

1. At glemme at opdatere `size`.
2. At glemme at rydde ubrugte pladser efter fjernelse.
3. At tilgå ugyldige indekser.
4. At eksponere samlinger direkte.
5. At duplikere logik til håndtering af samlinger.
6. At forveksle `size` og `capacity`.
7. At bruge arrays, når der er behov for dynamiske samlinger.
8. At placere logik til håndtering af samlinger uden for det ansvarlige objekt.
