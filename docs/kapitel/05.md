# Kapitel 5 – Invarianter

## 1. Introduktion

Session 5 introducerer en af de vigtigste idéer inden for objektorienteret design:

> Et objekt skal altid være gyldigt.

Fokus er på:

- invarianter
- validering
- konstruktørers responsibility (ansvar)
- setter-metoders responsibility
- exceptions
- immutable (uforanderlige) og mutable (foranderlige) objekter

Målet er at designe klasser, som beskytter sig selv mod ugyldig state.

---

## 2. Hvad er en invariant?

En invariant er en regel, som altid skal være opfyldt for et objekt.

Eksempler:

### Temperature

En temperatur kan ikke være lavere end det absolutte nulpunkt.

```text
celsius >= -273.15
```

### Rectangle

Et rektangel skal have positive dimensioner.

```text
length > 0
width > 0
```

### Student

```text
name må ikke være null eller tom
semester skal være mellem 1 og 10
email skal enten være null (for at angive, at ingen e-mail er oplyst) eller have et gyldigt format
```

Et objekt, der bryder sine invarianter, er ugyldigt.

---

## 3. Konstruktører skal etablere en gyldig state

En konstruktør har responsibility for at oprette gyldige objekter.

Eksempel:

```java
public Temperature(double celsius)
{
  if (celsius < -273.15)
  {
    throw new IllegalArgumentException(
        "Temperature cannot be below absolute zero.");
  }

  this.celsius = celsius;
}
```

Konstruktøren kontrollerer input, før værdierne tildeles.

Hvis input er ugyldigt, må objektet ikke oprettes.

---

## 4. IllegalArgumentException

`IllegalArgumentException` bruges, når en metode modtager ugyldigt input.

Eksempel:

```java
throw new IllegalArgumentException(
    "Temperature cannot be below absolute zero.");
```

Dette afbryder straks konstruktøren eller metoden.

Efter Session 5 bør ugyldigt input normalt medføre en `IllegalArgumentException`.

---

## 5. Test af exceptions

JUnit kan teste, at exceptions bliver kastet.

Eksempel:

```java
@Test void temperatureBelowAbsoluteZero()
{
  assertThrows(IllegalArgumentException.class,
      () -> new Temperature(-273.16));
}
```

Tests af exceptions er vigtige, fordi ugyldigt input også skal testes.

---

## 6. Validering i konstruktører

Validering betyder at kontrollere, om inputværdier er gyldige.

Eksempel:

```java
public Rectangle(double length, double width)
{
  if (length <= 0 || width <= 0)
  {
    throw new IllegalArgumentException(
        "length and width have to be positive");
  }

  this.length = length;
  this.width = width;
}
```

Validering beskytter objektets invarianter.

---

## 7. Flere invarianter

Klasser har ofte flere invarianter.

Eksempel:

```java
public Student(String name, int semester, String email)
{
  if (name == null || name.isBlank())
  {
    throw new IllegalArgumentException(
        "Name cannot be null or blank");
  }

  if (semester < 1 || semester > 10)
  {
    throw new IllegalArgumentException(
        "Semester must be between 1 and 10");
  }

  if (email != null &&
      (!email.contains("@") || !email.contains(".")))
  {
    throw new IllegalArgumentException(
        "Wrong email format: " + email);
  }

  this.name = name;
  this.semester = semester;
  this.email = email;
}
```

Hver invariant beskytter en del af objektets state.

---

## 8. Setter-metoder skal bevare invarianter

Konstruktører etablerer en gyldig state.

Setter-metoder skal bevare en gyldig state.

Eksempel:

```java
public void setSemester(int semester)
{
  if (semester < 1 || semester > 10)
  {
    throw new IllegalArgumentException(
        "Semester must be between 1 and 10");
  }

  this.semester = semester;
}
```

Et objekt skal være gyldigt efter hvert metodekald.

---

## 9. Undgå duplikeret validering

Valideringslogik bør ikke duplikeres.

Dårligt design:

```java
public Student(String name, int semester, String email)
{
  // validering her
}

public void setSemester(int semester)
{
  // den samme validering igen
}
```

Bedre design:

```java
public Student(String name, int semester, String email)
{
  this.name = name;
  setSemester(semester);
  setEmail(email);
}
```

Konstruktøren genbruger logikken i setter-metoderne.

Fordele:

- mindre duplikeret kode
- lettere vedligeholdelse
- mere ensartet validering

---

## 10. Konstruktørdelegering

Konstruktører kan delegere til andre konstruktører.

Eksempel:

```java
public Student(String name)
{
  this(name, 1, null);
}
```

Fordele:

- undgår duplikeret initialiseringslogik
- sikrer ensartet validering
- forbedrer læsbarheden

---

## 11. Mutable og immutable objekter

### Mutable objekter

Et mutable objekt kan ændre state efter oprettelsen.

Eksempel:

```java
student.setSemester(3);
```

### Immutable objekter

Et immutable objekt kan ikke ændres efter oprettelsen.

Eksempel:

```java
String
```

Immutable objekter er ofte lettere at arbejde med, fordi deres state aldrig ændrer sig.

---

## 12. Validering og responsibility

Validering hører hjemme i objektet.

God løsning:

```java
Student s = new Student("Bob", 3, "bob@builder.dk");
```

Dårlig løsning:

```java
if (s.getSemester() >= 1 && s.getSemester() <= 10)
{
  // ekstern validering
}
```

Objektet skal beskytte sig selv.

Det er en del af encapsulation (indkapsling) og responsibility.

---

## 13. Grænseværdier

Grænseværdier er særligt vigtige ved validering.

Eksempel:

```text
semester = 1   gyldig
semester = 10  gyldig
semester = 0   ugyldig
semester = 11  ugyldig
```

Tests bør omfatte:

- gyldige værdier
- ugyldige værdier
- grænseværdier

---

## 14. Test af invarianter

Tests bør kontrollere både:

- gyldig state
- ugyldig state

Eksempel:

```java
@Test void validSemester()
{
  Student s = new Student("Bob", 3, null);

  assertEquals(3, s.getSemester());
}
```

Eksempel:

```java
@Test void invalidSemesterThrowsException()
{
  assertThrows(IllegalArgumentException.class,
      () -> new Student("Bob", 11, null));
}
```

---

## 15. Typiske begynderfejl

Almindelige fejl:

1. At glemme validering.
2. At tillade ugyldig state.
3. At duplikere valideringslogik.
4. At validere uden for klassen.
5. At skrive setter-metoder, som bryder invarianter.
6. At glemme grænseværdier.
7. At oprette delvist initialiserede objekter.

## Opsummering

Session 5 handler om at beskytte et objekts gyldighed.

Vigtige idéer omfatter:

- invarianter beskriver en gyldig state
- konstruktører etablerer invarianter
- setter-metoder bevarer invarianter
- ugyldigt input bør medføre exceptions
- validering hører hjemme i objektet
- duplikeret validering bør undgås
- mutable objekter kræver særlig beskyttelse

God objektorienteret design handler om at skabe objekter, som altid forbliver gyldige.
