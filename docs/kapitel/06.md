# Kapitel 6 – Responsibility og encapsulation

## 1. Introduktion

Session 6 fokuserer på en af de centrale idéer i objektorienteret programmering:

> Objekter skal have responsibility for deres egne data og deres egen behavior.

Fokus er på:

- encapsulation (indkapsling)
- responsibility (ansvar)
- korrekt placering af logik
- static-metoder
- `LocalDate`
- exception-håndtering med `try-catch`

Målet er at designe klasser, som er læsbare, lette at vedligeholde og har responsibility for deres egen behavior.

---

## 2. Responsibility i objektorienteret design

Et objekt bør have responsibility for operationer, der vedrører dets egne data.

Eksempel:

Mindre god løsning:

```java
person.getAge() >= 18
```

Bedre løsning:

```java
person.isAdult()
```

Objektet skal selv afgøre, om det repræsenterer en voksen.

Det forbedrer:

- læsbarheden
- encapsulation
- vedligeholdelsen

---

## 3. Encapsulation

Encapsulation betyder:

- at beskytte interne data
- at kontrollere adgangen til state
- at stille meningsfuld behavior til rådighed

I stedet for at eksponere rå data bør objekter stille behavior til rådighed.

Eksempel:

Mindre god løsning:

```java
student.getEmail() != null
```

Bedre løsning:

```java
student.hasEmail()
```

Objektet skjuler interne detaljer og stiller meningsfuld behavior til rådighed.

---

## 4. Undgå at arbejde direkte på et objekts data

God objektorienteret design undgår at hente data ud af objekter for at arbejde med dem eksternt.

Mindre god løsning:

```java
email1.getDomain().equals(email2.getDomain())
```

Bedre løsning:

```java
email1.sameDomainAs(email2)
```

Logikken hører hjemme i den klasse, der har responsibility.

---

## 5. Fordele ved korrekt responsibility

Korrekt placering af responsibility giver flere fordele.

### Bedre læsbarhed

Eksempel:

```java
person.isAdult()
```

er lettere at forstå end:

```java
person.getAge() >= 18
```

### Mindre coupling (kobling)

Andre klasser behøver ikke kende interne detaljer.

### Lettere vedligeholdelse

Hvis logikken ændres, skal kun én klasse opdateres.

---

## 6. Gentaget logik er et advarselssignal

Gentaget logik er ofte et tegn på, at responsibility er placeret forkert.

Eksempel:

```java
if (email.getDomain().equals("dk"))
```

forekommer mange steder i programmet.

I stedet:

```java
email.isDanishDomain()
```

Objektet bør indeholde den logik, der vedrører objektet selv.

---

## 7. Beregnede data kontra lagrede data

Nogle oplysninger bør ikke gemmes direkte.

Eksempel:

Mindre god løsning:

```java
private int age;
```

Bedre løsning:

```java
private LocalDate birthDate;
```

Alder ændrer sig med tiden.

Fødselsdatoen er stabil og kan bruges til at beregne alderen.

Dette er en vigtig designbeslutning.

---

## 8. LocalDate

`LocalDate` repræsenterer datoer.

Eksempel:

```java
LocalDate birthday = LocalDate.of(2000, 10, 25);
```

`LocalDate` stiller en række nyttige metoder til rådighed.

Eksempel:

```java
birthday.isAfter(LocalDate.now())
```

Session 6 introducerer `LocalDate` som en bedre måde at modellere datoer på.

---

## 9. Validering af datoer

Datoer skal også overholde klassens invarianter.

Eksempel:

```java
if (birthDate.isAfter(LocalDate.now()))
{
  throw new IllegalArgumentException(
      "Birth date cannot be in the future");
}
```

Objektet skal afvise umulige datoer.

---

## 10. Static-metoder

En static-metode tilhører klassen og ikke et objekt.

Eksempel:

```java
private static LocalDate convertToDate(
    int day,
    int month,
    int year)
{
  return LocalDate.of(year, month, day);
}
```

Static-metoder er nyttige, når:

- metoden ikke afhænger af objektets state
- metoden fungerer som en hjælpemetode

---

## 11. Hjælpemetoder

Hjælpemetoder gør kompleks logik enklere.

Eksempel:

```java
private static LocalDate convertToDate(
    int day,
    int month,
    int year)
{
  // konverteringslogik
}
```

Fordele:

- forbedrer læsbarheden
- undgår duplikeret kode
- adskiller responsibilities

---

## 12. Konstruktørdelegering

Konstruktører kan delegere til andre konstruktører.

Eksempel:

```java
public Person(String name, int day, int month, int year)
{
  this(name, convertToDate(day, month, year));
}
```

Fordele:

- undgår duplikeret validering
- samler initialisering ét sted
- forbedrer konsistensen

---

## 13. Exception-håndtering med try-catch

Nogle operationer kan kaste exceptions.

`try-catch` gør det muligt at håndtere dem.

Eksempel:

```java
try
{
  return LocalDate.of(year, month, day);
}
catch (DateTimeException e)
{
  throw new IllegalArgumentException(
      "Illegal date", e);
}
```

Programmet forsøger at udføre operationen i `try`-blokken.

Hvis der opstår en exception, håndterer `catch`-blokken den.

---

## 14. Indpakning af exceptions

Nogle gange omdannes exceptions på lavt niveau til mere meningsfulde exceptions.

Eksempel:

```java
catch (DateTimeException e)
{
  throw new IllegalArgumentException(
      "Illegal date", e);
}
```

Klassen giver dermed en mere meningsfuld fejlmeddelelse, der passer til domænet.

---

## 15. Test af exceptions

Exception-håndtering bør også testes.

Eksempel:

```java
@Test void constructorRejectsIllegalDate()
{
  assertThrows(IllegalArgumentException.class,
      () -> new Person("Lars", 31, 2, 2000));
}
```

Tests bør kontrollere:

- gyldig behavior
- ugyldig behavior
- de korrekte exceptions

---

## 16. Gode designprincipper fra Session 6

### Spørg objektet

Foretræk:

```java
person.isAdult()
```

frem for:

```java
person.getAge() >= 18
```

### Undgå duplikeret logik

Placér logikken i den klasse, der har responsibility.

### Beskyt objektets state

Objekter skal selv bevare en gyldig state.

### Gem stabile data

Foretræk stabile data som `birthDate` frem for beregnede værdier som `age`.

---

## 17. Typiske begynderfejl

Almindelige fejl:

1. At placere logik uden for det ansvarlige objekt.
2. At eksponere for mange interne data.
3. At duplikere logik.
4. At gemme beregnede data unødvendigt.
5. At skrive static-metoder, som burde være instansmetoder.
6. At ignorere exceptions.
7. At fange exceptions uden at håndtere dem korrekt.

## Opsummering

Session 6 fokuserer på responsibility og encapsulation.

Vigtige idéer omfatter:

- objekter skal styre deres egen behavior
- logik hører hjemme i den ansvarlige klasse
- encapsulation beskytter objektets state
- duplikeret logik bør undgås
- stabile data er ofte bedre end beregnede data
- static-hjælpemetoder kan forenkle designet
- `LocalDate` giver bedre håndtering af datoer
- `try-catch` håndterer exceptionelle situationer

God objektorienteret design handler i høj grad om at placere responsibility det rigtige sted.
